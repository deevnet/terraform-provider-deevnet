# deevnet_alert_rule_group (Resource)

A group of alert rules over the tenant's metrics or its logs.

The rules run in the tenant's own vmalert on the site, reading with the tenant's log read token, so a rule sees exactly what the tenant's token sees. When a rule fires, and again when it clears, a notification goes to the ntfy topic `<tenant>-<topic>`, which the tenant's phone reads with `deevnet_tenant`'s `notify_username` and `notify_password`, on site.

The API has vmalert check every expression before it records the group, so a rule vmalert will not load fails the apply with the parse error. Alerting rules only: there are no recording rules. Requires API 0.25.0 and a site with alerting.

## Example Usage

```terraform
# Alerts over the tenant's own metrics, to the ntfy topic "<tenant>-backend".
resource "deevnet_alert_rule_group" "backend" {
  tenant = deevnet_tenant.this.name
  name   = "backend"
  type   = "metrics"
  topic  = "backend"

  rule {
    alert       = "QueueBacklog"
    expr        = "backend_queue_depth > 100"
    for         = "5m"
    labels      = { severity = "page" }
    annotations = { summary = "Queue is {{ $value }}" }
  }
}

# Alerts over the devices' logs from MQTT. A logs rule is LogsQL ending in a
# stats pipe; it fires for each row the query returns.
resource "deevnet_alert_rule_group" "doors" {
  tenant    = deevnet_tenant.this.name
  name      = "doors"
  type      = "logs"
  partition = "devices"
  topic     = "devices"

  rule {
    alert       = "DoorOpen"
    expr        = "\"door open\" | stats by (device) count() as hits | filter hits:>0"
    annotations = { summary = "{{ $labels.device }} opened {{ $value }} times" }
  }
}

# On the phone: the ntfy app, server notify_endpoint, logged in with
# notify_username and notify_password, subscribed to each group's ntfy_topic.
output "alert_topics" {
  value = [deevnet_alert_rule_group.backend.ntfy_topic, deevnet_alert_rule_group.doors.ntfy_topic]
}
```

## Schema

### Required

- `name` (String) 1-32 lowercase letters, digits or dashes, starting with a letter; unique within the tenant.
- `tenant` (String) The tenant this group belongs to: the `name` of a `deevnet_tenant`.
- `topic` (String) Where the group's alerts go: the ntfy topic `<tenant>-<topic>`. 1-32 lowercase letters, digits or dashes. Several groups may share a topic.
- `type` (String) `metrics`: each `expr` is MetricsQL (PromQL works) over the tenant's metrics. `logs`: each `expr` is LogsQL with a `stats` pipe, such as `"door open" | stats count() as hits | filter hits:>0`.

### Optional

- `interval` (String) How often the rules are evaluated, 30s to 1h. Default `1m`.
- `partition` (String) Which of the tenant's partitions the rules read: `workloads` (default), what the tenant's own workloads push; `platform`, what the site publishes about the tenant; or `devices`, the devices' logs from MQTT, for a `logs` group only.
- `rule` (Block List) An alerting rule. 1 to 50 in a group, and 200 across a tenant's groups. (see [below for nested schema](#nestedblock--rule))

### Read-Only

- `ntfy_topic` (String) `<tenant>-<topic>`, the topic to subscribe to on the phone.

### Nested Schema for `rule`

Required:

- `alert` (String) The alert's name: letters, digits and underscores, unique in the group.
- `expr` (String) The expression. The rule fires for each series (or `stats` row) it returns.

Optional:

- `annotations` (Map of String) Text for the notification, such as `summary`. vmalert templates work: `{{ $value }}`, `{{ $labels.host }}`.
- `for` (String) How long the expression must hold before the alert fires, such as `5m`.
- `labels` (Map of String) Labels added to the alert, such as `severity`. `tenant`, `deevnet_topic` and `alertname` are the platform's and are refused: the first two decide where an alert goes.
